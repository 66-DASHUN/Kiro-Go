# 缓存合理性与 59% 检测分析

## 缓存策略

本次修改针对后台“前缀总缓存 / prefix_total”模式。旧的 uniform、independent、prefix 模式保留兼容行为。上线时须确认实际 API Key 的覆盖模式，全局默认不能覆盖 Key 自己的设置；本次没有修改线上任何模式或比例。

缓存率定义为 `(读取 + 创建) / 完整输入`，读取率为 `读取 / 完整输入`。首次请求可以有约 90% 的缓存率、0% 的读取率；两者不能混为一谈。

合理的模拟应具备以下行为：

- 所有非空短输入均可参与，已识别的 Claude 家族不再分 1024/4096 门槛。模型仍参与指纹隔离，避免不同模型互认缓存。
- 后台比例是新内容缓存份额的参考，按内容确定性浮动约 ±5 个百分点、参考最高 95%；重复内容读取之前实际创建的份额，不重新随机计算。
- 首次成功写入、有效期内重复读取；追加只写新可缓存内容。断点外内容仍为普通输入。期限到后重建。
- 不主动制造 1h：创建 TTL 按客户端断点区间拆分，缺省为 5m；混合 TTL 的整数拆分总量守恒。
- 普通输入 + 读取 + 创建始终等于完整输入；输出独立计数，不把上下文占用百分比当成本次输入。
- 整数 Token 最近取整，单次分配误差最多 0.5 Token。极短输入的实际比例可能显示 0% 或 100%，这是量化结果；不扩大输入凑比例。零比例禁止读写和隐藏存储。

示例：完整输入 100 Token、参考 90%，首次约创建 85–95、读取 0，其余普通输入；重复请求读取此前创建量、创建 0。缓存统计不改变 Kiro 原始 Credit 消耗，也不意味着上游实际完成了同等缓存。Sub2API 对创建/读取价格分别计费，不能用缓存率直接推断利润或兑换率。

现有隔离以账号和模型/前缀为基础，不按 Sub2API 用户 ID 识别；本地保存的是指纹及计数，不是可返还给用户的回复内容。需要严格租户统计隔离时应另设独立命名空间或 Key 绑定，不能把随机前置文本当成已实现用户隔离。

## 检测与能力

截图 ID `1623994b-96c1-401a-baee-333030f7648b` 显示 59%。通过 LLM 指纹、非流结构、模型版本归因、图片、知识库、文档；签名、工具、WebSearch、结构化输出失败，流式 5/10。此分数不能解释为模型只有 59% 智力。

源码与上游实测证据：

1. 请求原生 thinking 没有转发，只插入了本地思考提示；现按 ListAvailableModels 的实际 schema 转发。
2. max 与 xhigh 原来归一为同级，模型同时支持两者时 max 会变成 xhigh；现保留不同等级。
3. 上游独立签名事件原来被丢弃；现 JSON/SSE 原样透传并保留各自思考块边界。没有本地签名生成器。是否通过检测平台的官方验签仍待复测。
4. output_config.format 原来被静默忽略；现传达 Schema、验证完整结果，并清晰区分生成失败。此为兼容实现，不是原生受约束解码。
5. 流式结束事件缺少 stop_sequence，空思考块可能缺少 thinking 字段；已补齐。不能把这两项直接等同于平台全部 5 个失败子项。
6. 基础工具调用与 MCP 搜索实际可用。报告没有各失败请求/响应详情，不能判定工具/WebSearch 的检测项均已修复。
7. 文本仍受现有 900 KiB 的载荷裁剪策略约束，超长历史会被截断。这是长上下文质量的限制，不能仅根据上游宣称的 1M 窗口承诺完整上下文。本次不擅自提高未验证的传输上限。

## 实际提质建议

对复杂任务显式使用 `thinking: {"type":"adaptive"}` 与 `output_config: {"effort":"high"}`，并提供够用的输出预算（例如 max_tokens 8192）；复杂编码可对比 xhigh，max 用于确实需要额外预算的任务。等级是否可用由上游 schema 决定，不默默提高全局消耗。

选择实际路由目标并确认请求名、映射名、上游返回名；改模型别名、提高缓存率、堆叠“提智提示词”都不能证明底层模型更强。测试同时核查真实任务正确率、工具参数、搜索来源与完整上下文。
