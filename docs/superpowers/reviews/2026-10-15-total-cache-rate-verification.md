# 总缓存率优化：本地验收报告

日期：2026-10-15。基线：`bdc07ba`，分支：`integration/kiro-reverse-2.1.0`。

## 结果与范围

已实现 `prefix_total`（前缀总缓存率）模式。后台比例控制 `(读取 + 写入) / 完整输入`，输出独立计数。此模式为本地统计模拟，不代表 Kiro 上游原生缓存遥测。

本轮只变更 Kiro 的配置兼容、缓存统计、协议接入、管理界面和测试文档。未推送、未部署、未迁移生产配置，未修改 Sub2API、其他服务或历史账单，未调用线上收费接口。

新配置和缺失模式的配置默认使用 `prefix_total`；明确保存的 `prefix` / `uniform` / `independent` 保留原比例语义。既有线上 Key 不会因本地开发自动切换。未来部署需单独迁移选定全局/Key 的模式，保留比例与启停设置。

## 核心计算验收

定义：完整输入 T、有效断点内前缀 C、未过期旧匹配 M、内容浮动后的参考率 p。

```text
B = min(C, floor(T × p))
R = floor(B × M / C)  # C > 0
W = B − R
I = T − B
```

单元测试固定有效 p=80%，验证：

| 场景 | T | C | M | R | W | I |
|---|---:|---:|---:|---:|---:|---:|
| 首次 | 10000 | 10000 | 0 | 0 | 8000 | 2000 |
| 完整重复 | 10000 | 10000 | 10000 | 8000 | 0 | 2000 |
| 追加内容 | 11000 | 11000 | 10000 | 8000 | 800 | 2200 |
| 断点覆盖不足 | 10000 | 2000 | 2000 | 2000 | 0 | 8000 |

始终检查 `I+R+W=T`、`W5m+W1h=W`。后台参考率 80% 的内容浮动范围为 75%–85%，95% 为 90%–95%；断点覆盖或模型门槛不足时实际总缓存率可更低。0% 和关闭均不读写、不创建或续期条目。

## 生命周期、校准和兼容性

- 实际写入断点与读取候选分离；移动标记时在含断点自身的 20 个位置内查找旧前缀，候选不能直接成为已写入条目。连续同类工具块按一组计位置。
- 成功结束后才提交；TTL 从请求开始时间计算，不因生成耗时而延长。零写入不能创建较短断点或把 5m 升为 1h；旧命中续期保留原 TTL。
- 输入计数在结束时沿用请求开始时快照校准，不再次查询缓存。Haiku 估算 3000 → 最终 6000 的冷请求写入，完整重复只读取、写入为零；向下校准后旧匹配低于 4096 时不读取、不续期。
- Sonnet 4.5 门槛 1024；Haiku 4.5、Opus 4.5/4.6 门槛 4096；未知模型在新模式下不报告缓存。
- Messages / Chat Completions / Responses 的 JSON 和 SSE 共 6 种协议组合均验证首次、重复、0% 请求。受控上游输入 10000、输出 137：缓存总量处于 7500–8500；首次 R=0，重复 W=0，0% 时 R=W=0，输出保持 137。
- 托管搜索成功提交使用模式感知更新，0% 不保存隐藏条目；既有失败整段不提交机制保留。
- 多 Key 的 80% 全局继承、95% 覆盖、0%、关闭及清除覆盖恢复继承，均通过 SQLite 重载测试。旧模式持久化测试通过。
- 新诊断接口沿用管理员鉴权、禁止浏览器缓存，最多 200 条 / 24 小时，管理界面显示最新 20 条。记录计数、比例、时间、规则及限制原因，不包含账号标识、密钥或请求原文。

## 已知支持边界

- 显式 TTL 来自 tools / system / messages 块级 `cache_control`；顶层 `cache_control` 暂未解析。无块级标记时沿用本地自动前缀模拟、缺省 5m，不声称实现官方所有缓存规则。
- 使用进程内缓存；重启后冷缓存及诊断清空属于预期行为。
- 诊断编号独立于历史账单 ID；本轮不增加贯通账单的请求 ID。
- 管理界面已检查 JS 语法与翻译完整性，未进行完整浏览器视觉验收。
- 尚未进行线上真实请求、Kiro Credit 与 Sub2API 实扣金额复核；不能从本地模拟测试推导固定 Credit 换算。
