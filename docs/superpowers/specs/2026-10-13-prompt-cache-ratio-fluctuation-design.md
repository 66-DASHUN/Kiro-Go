# Prompt Cache Ratio Fluctuation Design

## Goal

让后台填写的缓存比例成为每次请求的参考值，同时让缓存读写用量随输入内容和 Token 数产生可复现的小幅变化，避免所有完整命中请求都固定显示同一个百分比。

## Behavior

- 全局或 API Key 的缓存比例仍然是 `0` 到 `1` 的配置值。
- 有效比例以配置值为中心，上下浮动最多 5 个百分点。接近边界时缩小对称范围，例如 2% 使用 ±2 个百分点；0% 和 100% 保持精确。结果始终在 `0` 到 `1`。
- 浮动由请求的模型、dispatch 阶段的总输入 Token 数和完整输入指纹确定。同一输入重复请求得到同一比例，冷写入和热读取共享同一变化值。完成阶段沿用快照里的有效比例，不重新生成变化值。
- 首次请求按有效创建比例分配缓存写入；已有缓存命中时按有效读取比例分配缓存读取。
- 部分前缀命中仍只读取实际命中的前缀，整体读取率还会受到命中前缀占总输入的影响。
- 普通输入 Token 始终为 `max(total - cacheCreation - cacheRead, 0)`，缓存读写不会超过总输入。
- 输出 Token 不参与缓存比例计算，保留现有上游正数 usage 优先、未取得有效正数时使用输出估算的逻辑。这次修改不重写输出统计来源。
- 独立创建/读取模式分别对两个配置比例计算确定性浮动；统一模式继续使用同一配置比例。

## Implementation

在 `proxy/cache_tracker.go` 增加一个基于 SHA-256 的有效比例计算函数。`ComputeWithSettings` 和完成阶段的 `scalePromptCacheUsage` 使用同一有效比例，避免流式开始和结束阶段口径不同。删除固定 90% 读取上限，因为它会覆盖后台配置；有效比例本身已限制在 `[0,1]`。

Claude 无显式缓存标记时，为内容块保留默认五分钟断点，使旧消息和稳定系统内容可在追加新输入后复用。显式标记仍沿用现有标记和后续消息边界语义。所有断点使用整段输入的估算总量归一化，流式 message_start 先把缓存快照缩放到该事件使用的输入估算总量。

保持现有全局 / Key 配置和数据库结构；只更新界面说明，无新增设置。缓存仍按账号、模型、前缀和 TTL 判定，已有 Key 与账号绑定负责限制跨 Key 调度。实现只在本地工作树修改与验证，本次不推送、提交或部署。

## Verification

增加回归测试验证：同一输入结果可复现；不同输入在配置值上下 5 个百分点内且能产生不同结果；冷写入、热读取、部分前缀和流式完成阶段都满足 Token 守恒；禁用缓存后仍不产生缓存字段。运行 `go test ./... -count=1` 和 `go build ./...`。
