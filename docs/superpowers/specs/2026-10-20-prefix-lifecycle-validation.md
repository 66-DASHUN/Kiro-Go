# 前缀生命周期缓存模拟：验证记录

日期：2026-10-20。基于 `c166e2d` 增加独立的 `prefix_lifecycle` 模式，修改范围限于 Kiro 源码、管理界面和测试。本轮未连接服务器、未修改 Sub2API、未部署、未更改现有配置或默认模式。

## 参考证据与规则

参考本地 CCMAX 使用记录快照 `ops/kiro-reverse-release/ccmax-audit-20261015/usage.json` 中同一会话的连续记录：

| 时刻 | 普通输入 | 输出 | 缓存读取 | 缓存创建 |
|---|---:|---:|---:|---:|
| 13:33:35 | 2 | 1177 | 0 | 43046 |
| 13:33:54 | 2 | 531 | 43046 | 2710 |
| 13:34:06 | 2 | 408 | 45756 | 1366 |

这说明连续追加时，下一次读取量可以等于上次读取加创建；不能从这些计数单独推断该上游的内部实现或实际节省费用。

新模式根据内容实现该生命周期：首次完整写入可缓存前缀，重复读取有效前缀，追加只写新增可缓存部分，修改仅复用修改点之前仍匹配的前缀，过期则重新创建。比例参数不参与计算，不人为留下 10% 普通输入，不提高输出计数。

总输入和前缀使用稳定的本地语义块估算，包含工具定义、系统内容、消息和媒体。待生成的 assistant 消息头计入普通输入。显式缓存标记之后的未缓存内容也计入普通输入，因此普通输入取决于内容和边界，并非固定为 2 或强制非零。输出优先使用上游原生计数；缺失时沿用生成内容估算。

未提供缓存标记时，以内容块边界作为隐式 5m 检查点；短输入同样参与。仅显式 1h 标记产生 1h 写入。后缀的可复用期限受其依赖的前缀限制；移动标记不会把已经读取的 5m 前缀自动升级到 1h。

## 接口验证

本地受控上游返回原生输出 `137`、故意不可信的输入 `99999`。Messages、Chat Completions、Responses 的 JSON 与 SSE 六条路径均验证如下关系；这是测试样本，不是线上模型结果。

| 请求 | 总输入 | 普通输入 | 读取 | 创建 | 输出 |
|---|---:|---:|---:|---:|---:|
| 首次 | 165 | 2 | 0 | 163 | 137 |
| 重复，使用模型别名 | 165 | 2 | 163 | 0 | 137 |
| 追加消息 | 173 | 2 | 163 | 8 | 137 |
| 再重复，比例改成 0 | 173 | 2 | 171 | 0 | 137 |
| 关闭缓存 | 173 | 173 | 0 | 0 | 137 |

恒等式：总输入 = 普通输入 + 读取 + 创建；创建 = 5m 创建 + 1h 创建。OpenAI 协议的顶层输入字段包含缓存量；Messages 的 `input_tokens` 只表示普通输入。

验证还覆盖配置持久化、显式缓存边界保留、工具定义变化、编辑内容、混合 TTL 过期、长请求中途过期后续期、移动 TTL 标记、Key/账号/模型隔离、并发冷请求快照、关闭缓存、失败上游不预热、结构化校验失败不预热、托管搜索后续轮失败不预热，以及成功的托管多轮请求。

Chat 和 Responses 的归一化转换保留显式内容缓存标记。旧参考计量不变。每轮托管搜索的提交延后至整次请求成功；请求内没有临时命中叠层，所以首次冷请求的多个真实上游轮次可能各自写入共同前缀。

## 使用与限制

未来部署后，需在全局缓存模式或目标 API Key 的缓存覆盖中选择“前缀生命周期（按内容读写）”，并保持启用缓存；仍选 Sub2API 模式会继续执行固定参考项目规则。新模式隐藏比例输入框，诊断规则标记为 `prefix-lifecycle-v1`。

缓存以 API Key、上游账号、解析后的模型隔离；相同模型的点号/横线别名共用身份。共享一个出口 Key 的下游用户不会自动隔离。账号切换、模型变化、内容改变、TTL 到期和进程重启都可能使请求重新创建缓存。

本模式是本地用量模拟，不能证明上游真的缓存、降低 Kiro Credit 消耗或通过 CCTest。未执行线上上游或 CCTest 验证，尚未部署或切换生产模式。
