# Kiro 缓存模拟优化方案（已获准实施）

日期：2026-10-14。依据当天的只读使用记录审计及本地诊断，并按用户“后台设置的是缓存率，不是读取率”的纠正修订。用户已于 2026-10-15 授权本地实施。本文件保留计算设计并记录实施边界；线上服务、配置和 Sub2API 不在本轮变更范围。

目标：每个 API Key 的后台比例控制总缓存占比，读写拆分取决于内容匹配和缓存生命周期。保留内容浮动，减少重复写入，修复前缀回溯和模型门槛；只涉及 Kiro，不修改 Sub2API。

## 比例的准确含义

```text
总缓存率 = (缓存读取 R + 缓存写入 W) / 完整输入 T
读取占比 = R / T
写入占比 = W / T
普通输入 I = T − R − W
```

输出单独计数，不参与缓存比例。后台填写 80%，表示总缓存占比以 80% 为参考；不能解释成每次读取约 80%，也不能在首次请求中不受比例约束地写入全部前缀。

推荐新增语义明确的“前缀总缓存率”模式，作为新配置的默认。已有明确保存的模式保留原含义，不静默改变历史设置。实施时，用户当前使用的 Key 可按本方案迁移；保留原模式和设置以便回滚。

## 方案比较

| 方案 | 比例含义 | 完整重复请求 | 取舍 |
|---|---|---|---|
| **推荐：总缓存预算＋前缀生命周期** | 每 Key 比例控制读取与写入之和 | 旧内容匹配且未过期时，写入为零 | 满足用户的比例设置；属于统计模拟 |
| 严格前缀生命周期 | 不设人为总缓存率，由有效前缀决定读写量 | 可读取全部有效前缀，写入为零 | 生命周期更直接，但不能保证围绕后台比例浮动 |
| 继续使用当前公式 | 比例实际约束读取，剩余可缓存内容算写入 | 重复前缀仍被部分计为写入 | 保留已确认的重复写入问题，不推荐 |

采用第一项。它按比例调整统计分类，不代表上游原生缓存遥测，也不是物理 Token 子集的精确缓存实现。

## 核心分配规则

- T：完整输入 Token，沿用当前计数来源。
- C：有效缓存断点内、达到模型门槛的原始可缓存前缀。
- M：最长未过期、内容匹配的旧前缀，满足 0 ≤ M ≤ C ≤ T。
- p：该 Key 参考比例经内容浮动后的有效缓存率。
- B：本次允许报告的总缓存 Token 预算。

```text
B = min(C, floor(T × p))
R = floor(B × M / C)    # C > 0 时
W = B − R
I = T − B
```

C=0、未达到模型门槛、p=0 或模拟关闭时，B=R=W=0，I=T。始终满足 R+W=B、I+R+W=T，且各项非负。

这一算法将原始匹配区间 M 和新增区间 C−M 按同一系数 B/C 缩放为统计量。旧匹配部分中未报告为读取的份额归普通输入，不能再次计为新增写入。取整时将至多不足 1 Token 的余量归 W；M=C 时始终 W=0。

后台参考比例不是保证值：有效断点只覆盖 20% 输入时，即使填写 80%，最多也只能报告 20% 总缓存率；不能扩大断点或增加填充 Token 凑够比例。门槛判断针对原始累计前缀 C；缩放后的 B 可能小于该门槛，这是统计模拟与物理缓存的区别。

## 数字示例

前四项固定有效 p=80%，假设全部输入在有效断点内、已达到模型门槛；后两项演示断点覆盖不足与 0% 设置。实际 p 仍按后台比例随内容浮动。

| 场景 | 完整输入 T | 可缓存 C | 旧匹配 M | 读取 R | 写入 W | 普通输入 I | 总缓存率 |
|---|---:|---:|---:|---:|---:|---:|---:|
| 首次请求 | 10,000 | 10,000 | 0 | 0 | 8,000 | 2,000 | 80% |
| 完全重复、未过期 | 10,000 | 10,000 | 10,000 | 8,000 | 0 | 2,000 | 80% |
| 追加 1,000 可缓存 Token | 11,000 | 11,000 | 10,000 | 8,000 | 800 | 2,200 | 80% |
| 全部过期后重建 | 10,000 | 10,000 | 0 | 0 | 8,000 | 2,000 | 80% |
| 断点只覆盖部分输入 | 10,000 | 2,000 | 2,000 | 2,000 | 0 | 8,000 | 20% |
| 后台设置 0% | 10,000 | 10,000 | 10,000 | 0 | 0 | 10,000 | 0% |

## 内容浮动与多 Key

每 Key 设置覆盖全局设置。建议保留现有浮动范围：80% 参考对应 75%–85%；95% 参考对应 90%–95%，最高不超过 95%。同一 Key、模型、规范化输入在设置不变时产生稳定的 p；输入内容变化可使 p 上下浮动，不使用每次独立随机数制造差异。

这些范围控制总缓存预算。实际总缓存率还受断点覆盖、模型门槛和 Token 取整限制；读取占比还取决于 M/C。首次请求读取为零不代表总缓存率为零。

0% 与关闭均不报告读写、不创建或续期模拟条目；再次启用后，已有未过期条目可继续按生命周期规则判断，不人为复活过期条目。每 Key 的配置与统计独立；现有账号/模型隔离保持。

## 前缀回溯与模型门槛

分开保存“读取查找候选”与“实际写入断点”：

1. 按 tools → system → messages 顺序构建稳定内容块前缀指纹；缓存标记或位置变动不应改变相同内容的指纹。
2. 每个有效断点向前最多查找官方规则规定的 20 个内容块位置，找到先前成功建立且尚未过期的条目；内部零 Token 元数据不计为内容块。
3. 候选只用于查找，不能因为生成了候选指纹就视为曾写入；只在有效写入断点建立缓存条目。
4. 取满足门槛、内容、模型/账号隔离和 TTL 条件的最长匹配 M。标记移动到最新消息时，窗口内旧前缀仍可复用。

本次已复现的旧前缀 6,802 Token，在追加消息并移动标记后，应能匹配旧 6,802，不能仅退回 system 的 3,601。超过回溯范围、内容改变、换模型/账号或过期时，不伪造命中。

门槛按归一化后的实际模型判断：Sonnet 4.5 为 1,024；Haiku 4.5、Opus 4.5/4.6 为 4,096。门槛作用于原始累计前缀，不要求新增区间或缩放后的 W 独自达到门槛。未维护模型采用不模拟策略，不擅自增加 Token。

## TTL、续期与并发

保留客户端明确指定的 5m/1h，缺省 5m；后台总缓存率不控制 TTL。对原始新增区间按相应有效断点确定 TTL，再以 B/C 缩放为写入分类。采用最大余数法分配取整差额，使 W5m+W1h=W；没有新增写入时两项均为零。命中续期不增加 W。

匹配判断以请求开始时刻为基准。请求开始时固定账号、模型、比例、前缀与生命周期快照；成功结束后提交条目，TTL 的有效期由请求开始时间加 TTL 计算，不能因生成耗时而延长，已过期条目不复活。仅对新增区间的有效写入断点创建条目，零写入不能隐形建立较短断点或升级已有 TTL；真正命中的旧条目以原有 TTL 续期。失败不建立新条目或续期。继续使用进程内缓存，不增加 Redis 或持久化服务。

结束时如最终输入计数变化，沿用同一次请求的前缀快照校准 T/C/M，然后重新计算 B/R/W/I；不得重新查询被其他并发请求更新过的缓存。请求开始时即使估算低于门槛，也保留已存在、未过期的潜在匹配及其 TTL，最终计数达到门槛后才允许读取和续期；向下校准后低于门槛的旧匹配不能读取或续期。校准后重新检查边界与门槛。并发冷请求各自可能报告写入，保持请求开始时的一致状态。

Claude JSON/SSE、Chat Completions/Responses 及托管搜索逐轮聚合使用同一分配原则，避免重复结算。保持 I+R+W=T、W5m+W1h=W，输出独立计数。

## 可观察性与收费核对

后台分别展示“总缓存率”“读取占比”“写入占比”，并说明比例控制的是读写之和。诊断摘要记录独立诊断编号（当前使用记录没有可贯通的请求 ID，不声称该编号与历史账单 ID 对应）、规则版本、模式、T/C/M/p/B/R/W/I、TTL 写入分类及限制原因，不保存原文、密钥或令牌；设置记录容量和保留期限。

对外 usage 字段保持兼容，Sub2API 继续按接收到的 I/R/W 与现有模型价格、分组倍率扣费。新方案会改变计费分类，具体金额需要实施后用受控请求重新核对；不沿用旧规则下的 Credit 换算，不重算历史账单。

## 实施与验收建议

本轮实现 `prefix_total` 新模式。显式 `prefix` / `uniform` / `independent` 的比例公式保留；Haiku 4.5 的错误最低门槛修正为 4,096。生产部署时，应明确将用户当前的全局及所选 Key 从旧 `prefix` 切换到 `prefix_total`，保留原比例与启停设置；本轮不执行该生产迁移。

| 验证场景 | 验收标准 |
|---|---|
| 首次、重复、追加、过期 | 读写总量受缓存预算约束；完整重复 W=0；追加只对新段分配写入 |
| 移动标记、修改前缀、换模型/账号 | 窗口内旧内容可命中；不满足隔离或内容条件时无旧命中 |
| Haiku 4.5 前缀 4,095 / 4,096 | 前者不模拟，后者允许；门槛检查原始累计前缀 |
| Sonnet 4.5 前缀 1,023 / 1,024 | 前者不模拟，后者允许 |
| 多 Key 80%/95%、0%、关闭 | 读写之和围绕参考值，受有效断点限制；0% 与关闭读写均为零 |
| 同一内容重复与内容变化 | p 稳定可复现，变化可浮动；不逐次随机 |
| 混合 TTL、命中续期 | TTL 分项等于 W，续期不增加写入 |
| 流式/非流式、计数校准与并发 | 固定请求快照、所有分项非负、总输入守恒、输出独立 |

实施及上线仅涉及 Kiro，保留已有账号、Key、绑定、并发、路由、域名和端口。发布保存旧镜像/配置，只替换 Kiro，核对其他服务状态。进程重启导致冷缓存属于正常行为，需区别于错误重复写入。

## 本轮协议支持边界

Claude 的显式 TTL 当前来自 tools / system / messages 内容块级 `cache_control`。没有块级标记时沿用本地自动前缀模拟、缺省 5m；不声称实现官方全部自动缓存规则。顶层 `cache_control` 暂未解析，不属于本轮新增协议支持。未知模型的总缓存率模式不报告读写。

诊断接口为 `/admin/api/prompt-cache/diagnostics`，使用现有管理员鉴权；最多 200 条 / 24 小时，后台显示最新 20 条。每条记录使用独立编号，只含计数、时间、比例与限制原因，不包含账户标识、密钥、请求内容。仅新模式的成功请求被记录；关闭模拟不生成诊断。
