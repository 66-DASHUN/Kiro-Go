# 单账号并发配置

用户要求每个账号默认 5 并发，沿用按真实账号合并计数、满额排队的方案。

## 配置与兼容

账号新增 `maxConcurrency`，后台账号详情可修改为正整数。新账号默认保存 5；旧数据库、导入文件和旧备份没有该字段时按 5 生效，无需修改旧数据。账号列表与完整详情返回有效值。配置补丁、刷新凭证、后台状态更新、备份恢复均保留该设置；后台状态的旧快照不能覆盖新配置。

## 调度边界

在共享的 `CallKiroAPIContext` 入口获取账号名额，返回时释放。名额覆盖完整流读取、错误及端点内部重试。Claude Messages、OpenAI Chat、Responses、管理测试和托管搜索的模型阶段共用同一限制，与下游 API Key、模型及是否流式无关。独立的托管 MCP 搜索调用也使用同一限制；模型调用完成后再搜索，避免嵌套获取。

以稳定账号 ID 为键；无 ID 的旧内存对象使用凭证指纹作为兼容键。不同账号独立排队。等待按先到先服务，取消等待不发起上游调用。每个调用只释放一次；空闲队列删除，避免留下永久内存条目。

后台修改即时生效：提高上限唤醒等待者；降低上限让已有调用完成，活跃数低于新上限后才接收新调用。获取、唤醒和释放时读取最新持久配置，防止旧账号快照覆盖新设置。

## 错误与边界

排队最多等待 60 秒（客户端超时或断开可更早结束），超时返回本地 429。使用现有客户端错误类型，避免触发上游额度耗尽、账号冷却或封禁处理。不得改变已有重试、额度切号、缓存模拟、账号绑定或 Sub2API 配置。本限制在一个 Kiro 进程内生效，符合当前单容器部署。

## 验证

验证默认 5、第 6 个等待、流读取期间持续占位、三个协议与流式混合计数、不同账号独立、排队取消、异常释放、动态升降、等待超时不导致账号冷却，以及两种持久化模式中配置更新和旧快照保留。运行 Go 全套测试、vet、并发 race 检查、Linux 构建，并检查中英文前端与保存行为。
